# Governance

This app turns uploaded documents into a support assistant that can be embedded
on any website. Documents are indexed on the server and kept either in server
memory (demo) or in a Postgres database the user connects. By default each
answer is generated by a model on Groq and spends the deployment's Groq quota.
A site owner can attach their own OpenAI-compatible model instead; answers for
that owner's preview and embeds then come from that model and spend the
owner's provider credits. This file records what is enforced, where the data
goes, and what is still open. It describes controls; it is not a
certification.

## What a caller can and cannot do

| Can | Cannot |
| --- | --- |
| Upload TXT, MD, PDF or DOCX files up to 10 MB each | Choose where an upload is written on disk |
| Chat with the documents of a session whose ID it holds | Discover other sessions' IDs from the API |
| Create a widget from a session it holds, optionally limited to up to 10 listed sites | List, export or delete other users' data |
| Attach its own OpenAI-compatible model; saving it sends one test request, up to 5 checks per minute per IP, per server instance | Make the server call a model address on localhost, a private network or a link-local address (unless the operator opts in), or follow a redirect from a model address |
| Use a model token in its own builder preview and when generating an embed | Use a model token as a widget key or database token, or a builder or widget token as a model token |
| Send up to 20 chat requests and 10 uploads per minute per IP, per server instance | Send prompts or messages beyond the size caps |
| Connect its own Postgres database, up to 5 attempts per minute per IP, per server instance | Make the server connect to localhost, private-network or link-local addresses (unless the operator opts in) |
| Use a builder token for its own database's workspace | Use a widget token on builder routes, or a builder token as a widget key |
| Read and write the `support_bot` tables of a database whose token it holds | Run SQL of its choosing through the app, or reach another workspace in the same database through the API |

## Controls

| Control | Where | What it prevents |
| --- | --- | --- |
| Random temp file names | `src/app/api/upload/route.ts` | The uploaded filename is never part of a path, so `../` in a name cannot write or delete outside the temp directory. |
| Unguessable IDs | `generateUUID` in `src/lib/database.ts` | Session IDs, widget keys and keys come from `crypto.randomUUID()`, not the predictable `Math.random`. |
| No debug route | removed `src/app/api/debug` | Nothing lists sessions or documents, and nothing wipes the store, without authentication. |
| Rate limits | `isRateLimited` in `src/lib/guard.ts`, called first in every route | One client cannot run unbounded requests against the Groq key, an owner's provider key or the server's CPU. |
| Input size caps | `LIMITS` in `src/lib/guard.ts` | Messages are capped at 2,000 characters and custom system prompts at 4,000. |
| Allowed sites (exact origins) | `src/lib/origins.ts`; `widgetOriginAllowed` and `widgetCorsHeaders` in `src/lib/guard.ts`; `src/app/api/widget/chat/route.ts` and `src/app/api/widget/script/[key]/route.ts` | Sites entered in the builder are normalised to `scheme://host[:port]` and matched exactly: `https://www.example.com`, `http://example.com` and `https://example.com:8443` are all different from `https://example.com`. The chat route refuses a request whose `Origin` is not listed, including a missing or `null` one, with 403 before any retrieval or model call. Its response to an allowed origin echoes that origin with `Vary: Origin`, never `*`; a refused request gets no `Access-Control-Allow-Origin`. The script route refuses with 403 and `Cache-Control: no-store` when the `Origin`, or else the origin of the `Referer`, is not listed. The list travels inside the `sbw2_` embed token. Without `EMBED_TOKEN_KEY` it is kept with the demo widget in server memory. A demo widget issued as `sbw2_` is marked sealed, so its plain `widget-…` key is not found. |
| Legacy domain allowlist | `originAllowed` in `src/lib/guard.ts`, used by `src/app/api/widget/chat/route.ts` | Applies only to the `allowed_domains` field of widgets that already have one. It matches the hostname and any subdomain and ignores scheme and port. The builder never writes to it, and the script route does not check it. |
| Documents marked as data | `wrapDocuments` and `DOCUMENTS_RULE` in `src/lib/llm.ts` | Retrieved text is fenced in `<documents>` and the model is told not to follow instructions inside it. |
| Loud failures | `generateEmbeddings` in `src/lib/embeddings.ts`, `generateResponse` in `src/lib/llm.ts` | A failed embedding fails the upload instead of storing a zero vector and reporting success. A failed chat call returns an error instead of a canned answer that looks like a working bot. |
| Calibrated retrieval | `MIN_SIMILARITY` in `src/lib/embeddings.ts` | Passages are used only above a cut-off measured for the embedding model, so an unrelated question gets a general answer instead of loosely related passages. |
| No unbacked claims | `src/app/page.tsx`, `README.md` | Made-up analytics, a stub audit log, stub SSO and invented customer metrics were removed. |
| Purpose-bound encrypted tokens | `src/lib/storage/token.ts` | Connection credentials reach the browser and embed code only encrypted with AES-256-GCM under `EMBED_TOKEN_KEY`. The prefix (`sbb1_` builder, `sbw1_` and `sbw2_` widget, `sbm1_` model) is authenticated data and must match the purpose inside, so a token cannot be edited, or relabelled to another purpose, without failing to decrypt. Builder routes refuse widget and model tokens in `x-storage-token`, widget routes refuse builder and model tokens, and `x-model-token` refuses builder and widget tokens, all before decrypting. |
| Model credentials in tokens | `sealModelToken` and `sealWidgetTokenV2` in `src/lib/storage/token.ts`; `src/lib/model/resolve.ts` | An owner's API key, base URL and model ID reach the browser only inside an `sbm1_` model token, and the embed code only inside the `sbw2_` widget token, both encrypted as above. `sbw2_` is compressed (deflate-raw) before encryption and decompressed only after the authentication tag verifies, with output capped at 16 KB. On opening, every field is checked again against the input caps. The validate route returns the token, the model ID and the host only; generate's response carries the token and no model fields. The server does not store them. |
| Model address guard | `checkModelBaseUrl` and `guardedLookup` in `src/lib/model/url-guard.ts`, run on every call by `src/lib/model/openai-compatible.ts` | Base URLs must be `https:`, with a host and no user name, password, query or fragment. Literal IPs, including forms such as `2130706433`, and every address a host name resolves to are classified with `classifyAddress` from `src/lib/storage/connection.ts`. Loopback, private, link-local (including `169.254.169.254`), CGNAT, multicast and reserved addresses, and `localhost` and `*.localhost`, are refused unless `ALLOW_PRIVATE_MODEL_HOSTS=1` or `NODE_ENV=development`; with that flag, plain `http:` is allowed only to non-public addresses. The socket connects only to addresses from the answer that was checked. Sockets are not reused (`agent: false`), and redirects are not followed: a 3xx is reported as an error. |
| Bounded model requests | `src/lib/model/openai-compatible.ts` | Output is capped at 1,024 tokens. Chat calls time out after 30 s and the validation call after 10 s. Reading the response stops past 1 MB, and the request asks for an uncompressed body. `reasoning_effort` is sent only for model IDs containing `gpt-oss`; other models get `model`, `messages`, `max_tokens` and `temperature` only. |
| Mapped provider errors | `MODEL_ERROR_MESSAGES` in `src/lib/model/shared.ts`; `src/lib/model/openai-compatible.ts` | Every model failure becomes one of a fixed list of codes with a fixed message. On failure, the only value passed on from the provider's reply is an integer HTTP status, shown as "The provider returned an error (HTTP n)." Provider bodies and headers, and raw socket, TLS and DNS errors (which contain host names), are never returned or logged. Each call logs one line: `model call provider=demo\|owner model=#<fingerprint> outcome=<ok or code> ms=<n>`. |
| No fallback to Groq | `src/app/api/chat/route.ts`, `src/app/api/widget/chat/route.ts` | With an owner model attached, every chat-model call goes to it. If it fails, the preview returns 502 with the code and fixed message, and the widget returns 503 "Widget unavailable". The answer never comes from Groq instead. If query rewording fails, the preview searches with simple variations of the question built without a model. |
| Model validation limit | `src/app/api/model/validate/route.ts` | 5 checks per minute per IP, per server instance. At most 8 KB of request body is read. All field caps (base URL 500 characters, model ID 200, key 512) are checked before any network access. A check sends one request with at most 16 output tokens and a 10 s timeout. |
| Connection-string validation | `validateConnectionString` in `src/lib/storage/connection.ts` | Only `postgres://`/`postgresql://` with one host and at most 1,000 characters. Parameters that redirect the connection or load files (`host`, `hostaddr`, `options`, `sslrootcert` and others) are rejected; everything except `sslmode` is dropped. Public hosts must use TLS; with no `sslmode` the certificate and host name are checked. |
| Private-host block | `connection.ts`, DNS check in `src/lib/storage/pg-pool.ts` | Loopback, private, link-local, CGNAT, multicast and reserved addresses are refused, both as literals and as what a host name resolves to, unless `ALLOW_PRIVATE_DB_HOSTS=1` or `NODE_ENV=development`. The pool connects to the checked IP, with TLS still verifying the original host name. |
| Bounded pools and timeouts | `POOL_LIMITS` in `src/lib/storage/pg-pool.ts` | At most 20 pools of 3 connections per instance, least recently used evicted, idle pools closed after 10 minutes. Connects time out after 5 s; statements, queries and idle transactions after 10 s. Concurrent first requests share one pool. |
| Fixed error codes | `src/lib/storage/errors.ts` | Database errors are mapped to a fixed list of codes with fixed messages. Driver messages, which can contain the user name and host, are never sent to the browser or logged; logs show only the code. |
| Workspace-scoped queries | `src/lib/storage/pg-store.ts` | Each store is bound to the workspace in its token; every query filters by that workspace and uses fixed SQL with `$n` parameters. A widget is only found inside its own workspace. |
| Connect rate limit | `src/app/api/storage/connect/route.ts` | Connection attempts are limited to 5 per minute per IP, so the server cannot be used to probe many hosts quickly. |
| No destructive DDL | `ensureSchema` in `src/lib/storage/schema.ts` | The app creates `support_bot` objects only when they are missing, and only from the connect route. It never runs `CREATE EXTENSION`, `DROP`, `TRUNCATE` or `ALTER`. Tables made for another schema version or embedding size are refused, not changed. |

## Where data goes

### Demo (no database connected)

- **Stays on the server:** uploaded documents are embedded in-process with
  `all-MiniLM-L6-v2`. Their text is not sent anywhere to be indexed. The
  model's weights are downloaded once from Hugging Face; that download sends
  no user data.
- **To Groq** (when no owner model is attached; see
  [With your own model](#with-your-own-model)): every visitor question with
  the matching passages, to generate
  the answer (`openai/gpt-oss-20b` unless `GROQ_MODEL` says otherwise). In
  the builder's preview chat the question is also sent once more first, so the
  model can reword it for search; the widget does not do this. By default Groq
  may store the inputs and outputs of each request for up to 30 days, for
  reliability and compliance. The organisation's *Inference APIs ZDR* setting
  (Settings, Data Controls) turns that off. Enable it before real visitor
  traffic.
- **To server memory:** documents, chunks, embeddings and widget settings,
  held in `Map`s in `src/lib/database.ts`. They are lost when the server
  instance restarts, and different instances do not share them.
- **To the browser:** answers, the names of the source files used, and a
  retrieval match score.
- **To the server log:** request diagnostics, including filenames and the
  length of each question. The text of visitor questions is not logged.

### Connected database

- **To the user's database:** documents (filename and a 200-character
  preview), chunks, embeddings and widget settings, in the `support_bot`
  schema. Documents uploaded before connecting are copied there from server
  memory when the user connects.
- **Still through this server, and to Groq:** each visitor question and the
  matching passages pass through this server and go to Groq, exactly as in
  demo mode, or to the owner's model when one is attached. Embedding still
  runs on this server. Connecting a database does not change what the model
  receives.
- **In the token:** the builder token (kept in the browser's `localStorage`)
  and the widget token (inside the embed code) both contain the connection
  credentials, encrypted with the server's key, `EMBED_TOKEN_KEY`. The server
  does not store the connection string; it holds it in memory only while a
  connection pool to that database is open.
- **Who can recover the credentials:** anyone holding both a token and
  `EMBED_TOKEN_KEY` can decrypt the connection string, user name and password
  included.
- **Revocation:** there is no per-token revocation. Rotating the database
  password is the way to revoke, and it breaks every existing token and embed
  for that database. Connections already open survive a password change until
  they close or are terminated (`pg_terminate_backend`).
- **Rotating `EMBED_TOKEN_KEY`** invalidates every token, for every database.
- **To the server log:** a short fingerprint of the connection (`db=` plus 8
  hex characters of a SHA-256 hash), the first 8 characters of the workspace ID,
  token fingerprints instead of tokens, and mapped error codes. Never the
  connection string, a token, or a driver error message.

### With your own model

- **To the owner's model address instead of Groq:** each question and the
  matching passages go from this server to the base URL the owner saved, to
  generate the answer. In the builder's preview the question is also sent
  there first to be reworded for search. That only happens when this server
  instance has no cached rewording for the same model address and question.
  The cache key is the provider kind, a fingerprint of the base URL and model
  ID, and a fingerprint of the question. The widget does not reword.
  Embedding still runs on this server; document text is never sent anywhere
  to be indexed.
- **When saving the model:** one test request ("Reply with the word OK.",
  at most 16 output tokens) goes to the address. The provider may bill for it.
- **Retention:** the provider's data retention policy applies. Groq's ZDR
  setting above has no effect on an owner's model.
- **In the token:** the browser keeps the `sbm1_` model token in
  `localStorage` (`ai-support-bot.model`), next to the model ID and host shown
  in the builder. The embed code carries the API key inside the `sbw2_` widget
  token. Both are encrypted with `EMBED_TOKEN_KEY`. The server does not store
  the key; it decrypts the token on each request.
- **Who can recover the key:** anyone holding both a token and
  `EMBED_TOKEN_KEY`.
- **Revocation:** "Remove model" in the builder deletes only this browser's
  copy. Embeds already generated keep using the key until it is revoked at the
  provider. Generating a new tag does not disable the old one.
- **To the server log:** a fingerprint of the base URL and model ID (8 hex
  characters of a SHA-256 hash), the outcome code and the duration. Never the
  key, the base URL, a provider response or a provider error message.
- **Allowed sites:** with `EMBED_TOKEN_KEY` set, the list is stored only
  inside the encrypted `sbw2_` token. Without it, the list is kept with the
  demo widget in server memory.

## The retrieval match score

The API calls it `confidence`; the UI labels it a match score. It comes from
`matchScore` in `src/lib/embeddings.ts`: the best passage's cosine similarity,
placed on a 0 to 100 scale between `MIN_SIMILARITY` (0.15) and
`STRONG_SIMILARITY` (0.5). It is 0 when no passage was used. It measures how
closely a passage matches the question. It does not measure whether the answer
is correct.

The cut-offs were measured against `faq.md`. Passages that answer a question
scored 0.18 to 0.57; for unrelated questions the best passage scored under
0.10. Some answers rank below other passages, because chunks are fixed
1,000-character slices that can split an answer.

Earlier versions returned a different number from the widget route: 85 to 95
whenever the model's answer was long. Neither widget script displays the
field, but API clients could read it. That number is gone.

## Known gaps

- **Retrieval quality is measured on one document.** The cut-offs suit
  `faq.md`; other documents may need different values.
- **No authentication.** Anyone can use the builder, and a session ID is the
  only thing protecting a session's documents.
- **Rate limits are per instance.** On a platform that runs many instances, the
  effective limit is higher, and a restart resets the counts. This includes the
  limit of 5 database connection attempts and 5 model checks per minute.
- **Rate limits trust the client IP headers.** `clientIp` in
  `src/lib/guard.ts` uses `x-real-ip`, then the first entry of
  `x-forwarded-for`. Vercel overwrites these headers with the caller's address.
  On a host that passes them through from the client, a caller can change them
  on every request and get around the per-IP limits.
- **Allowed sites rely on the browser's `Origin` and `Referer` headers.** They
  stop other websites using a widget in visitors' browsers. A non-browser
  client can send any `Origin`, so anyone who copies the embed token can call
  the chat API directly. The list is also opt-in, except for embeds that use
  an owner model: an empty list allows every site.
- **Preflight is permissive.** `OPTIONS` on the widget chat route answers `*`
  for every origin, because a preflight request carries no widget key. The
  list is enforced on the `POST`.
- **The script is served when neither header is present.** With no `Origin`
  and no `Referer` (for example under `Referrer-Policy: no-referrer`), the
  script route serves the widget script, including its title and welcome
  message. The chat route still refuses the questions.
- **Visitors on allowed sites spend the owner's credits.** Anyone using an
  allowed site, and anyone calling the chat API directly as above, can send up
  to 20 questions a minute per network, per server instance, to the owner's
  model. There are no spend caps.
- **No per-token revocation for model keys.** The way to cut off an embed or a
  saved model is to revoke or rotate the API key at the provider, which breaks
  every embed that uses it.
- **The builder's model token is a bearer credential.** It is encrypted, but
  anyone who copies it from the browser's `localStorage` can use it on this
  deployment's preview and generate routes to spend the owner's credits.
- **DNS rebinding for model addresses.** Each request resolves the host once
  and connects only to addresses from that same answer, all of which passed
  the check. Sockets are not reused and redirects are not followed, so there is
  no check-then-connect gap. A rebinding DNS answer is re-checked on the next
  request.
- **Fencing documents reduces prompt injection; it does not prevent it.** A
  document written to manipulate the model can still influence answers.
- **No retention control, and no delete-my-data UI.** Demo data lasts until
  the instance restarts. Connected data lasts until the database owner deletes
  it; the app has no way to delete documents, widgets or a workspace, and the
  least-privilege role has no `DELETE` right.
- **Credentials in the token have read-write access.** Builder and widget
  tokens carry the same connection string. The widget token is limited to
  widget routes by the app only; anyone who can decrypt it gets the role's
  full rights (`SELECT`, `INSERT`, `UPDATE` on `support_bot` with the
  least-privilege role, or the owner's rights if the user connected as owner).
- **The private-host check resolves DNS once, when a pool is created.** The
  pool then connects to that IP for its lifetime (up to 10 minutes idle, longer
  if in use). A DNS change during that time is not re-checked; DNS rebinding
  during a pool's lifetime is not addressed.
- **Embed tokens are public.** A widget token sits in the page source and in
  hosting providers' access logs. It is encrypted, but it works as a bearer
  key: anyone who copies it can use the widget's chat API from any client
  that sets an allowed `Origin`. For an embed with an owner model, that spends
  the owner's credits.
- **`sslmode=require` does not verify the certificate.** It is offered for
  providers whose CA Node does not trust (Supabase); it encrypts but does not
  stop an attacker on the network path who can present any certificate.
- **One server key protects every token.** `EMBED_TOKEN_KEY` leaking exposes
  the credentials in every token issued with it, every owner's model API key
  included, and rotating it breaks all of them.
- **Session IDs appear in the server log.** The preview chat and upload
  routes and the in-memory store log session IDs in full. A session ID is the
  only thing protecting a demo session's documents, so anyone who can read the
  log can read those documents through the API.
- **A second demo widget takes over the first one's documents.** Generating
  another widget from the same demo session moves the session's passages to
  the new widget (`createWidgetFromSession` in `src/lib/database.ts`). The
  older widget keeps answering, but without those passages.

## How the controls were checked

Against `npm run build && npm start`:

- `GET /api/debug` returns 404.
- An upload named `../../../evil-test.txt` is written to
  `<tmpdir>/upload-<uuid>.txt`.
- The 21st `/api/chat` call from one IP within a minute returns 429.
- A 5,000-character system prompt returns 400.
- With `faq.md` uploaded, "What file types can I upload?" retrieves three
  passages; "What is the capital of France?" retrieves none.
- `originAllowed` accepts `shop.example.com` for `example.com` and rejects
  `example.com.evil.com`, `notexample.com` and a missing origin.

Unit and route tests (`npm test`, no network and no real keys):

- `src/lib/__tests__/origins.test.ts`: origin normalisation, every inline
  error, list caps and duplicates, and the exact-match table
  (`https://example.com` and `:443` accepted; `http://`, `www.`, `:8443`,
  `example.com.evil.com`, `notexample.com`, `null` and a missing origin
  refused). It also covers the legacy `originAllowed` cases above and the CORS
  headers for each policy.
- `src/app/api/widget/__tests__/widget-routes.test.ts`: the chat route
  refuses an unlisted, missing or `null` `Origin` with 403 and no
  `Access-Control-Allow-Origin`, without calling retrieval or the model. An
  allowed origin is echoed with `Vary: Origin`, a widget with no list keeps
  `*`, and legacy lists keep subdomain matching. The script route refuses an
  unlisted `Origin` or `Referer` with `no-store`, and serves the script when
  neither header is present.
- `src/app/api/widget/__tests__/owner-model-routes.test.ts`: with an owner
  model the widget and the preview call only that model. An owner-model
  failure returns 503 from the widget and 502 with the fixed message from the
  preview, and the demo model is not called. The key and base URL are not
  logged. Generate refuses a model without allowed sites before creating
  anything, and returns an `sbw2_` token with no model fields. A missing
  `GROQ_API_KEY` still returns 500.
- `src/lib/model/__tests__/url-guard.test.ts`: `http://` public hosts,
  `https://127.0.0.1`, `https://[::1]`, `https://[::ffff:127.0.0.1]`,
  `https://169.254.169.254`, `https://10.0.0.1`, `https://2130706433` and
  `localhost` are refused. User info, query, fragment and over-long input are
  refused before any DNS lookup. A host name whose (mocked) DNS answer
  includes a private address is refused.
- `src/lib/model/__tests__/openai-compatible.test.ts`, against a local mock
  server: each provider error class maps to its fixed code, and the error's
  message is the code itself. A 401 key rejection, for example, becomes
  `model_auth_rejected`, shown as "The provider rejected this API key." rather
  than the provider's text. Timeouts and bodies over 1 MB are
  stopped, and a 302 is not followed (the mock sees one request). Request
  bodies follow the `gpt-oss` split with output capped at 1,024 tokens. A
  sentinel placed in the mock's body and headers, and the API key, appear in
  no log line or error.
- `src/lib/model/__tests__/model-token.test.ts` and
  `src/lib/storage/__tests__/token.test.ts`: tokens round-trip; any changed
  character, wrong key or relabelled prefix fails to open; the key and base
  URL path are not readable in a token; an `sbw1_` token sealed by the
  earlier code still opens. Over 200 seeded worst cases, the largest `sbw2_`
  token is 7,273 characters and its script URL 7,388.
- `src/lib/storage/__tests__/resolve.test.ts`: each widget's policy comes from
  where its list is stored, a sealed demo widget is not found by its plain
  key, and a model token is refused as a widget key and as a database token.
